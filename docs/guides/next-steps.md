# Next-step handoffs

You do not need to know CE's skill catalog to continue a task. When a skill finishes or stops with unfinished work, its user-facing handoff recommends the next action and explains what that action will accomplish. When a CE skill fits, the handoff names it and supplies a copyable prompt. Alternatives appear when they offer a meaningful choice.

The handoff says whether to stay in the current thread or open a new thread in the same project. Your preference takes precedence. By default, unresolved dialogue stays in the current thread; a distinct stage can start in a new thread when its context can be carried reliably.

A new-thread prompt carries the objective, the relevant project or checkout, actual artifact paths, decisions, constraints, and expected result. It includes the branch or worktree when needed. A saved `ce-handoff` document and its copyable resume command can carry that context instead. Temporary and machine-local paths are labeled so their limits are visible.

A blocked run explains what is missing, who can supply it, and how work resumes. For example, requirements-only input needs implementation planning before `ce-work` can build it. A missing credential needs access from its owner. Repeating a blocked invocation does not satisfy either prerequisite. A checklist or recording instructions do not establish that a requested executable deliverable was built or verified.

This guidance supplements each skill's existing menu and completion report. It does not authorize another workflow or open a thread automatically. Already-authorized work continues within the active workflow. Internal calls preserve their structured results so the outer workflow owns the user's handoff. Output-only contracts and explicit requests to stop remain authoritative. A completed goal with no useful remaining action ends without an invented task.

Copyable invocations follow the current host: slash form by default, dollar form on Codex, and oh-my-pi's native form for skills that are hidden or manual-only.
