# Reviewer Dispatch

Read this before dispatching the Step 2 reviewers. It covers the reviewers' model, what happens when the harness is full, how review agents are released, and the permission mode.

**Model selection.** Use the platform's balanced mid-tier model for these reviewers when the current harness exposes a known override. In Claude Code this is the Sonnet class. In Codex, apply this tier only when the active dispatch primitive exposes an explicit model or custom-agent selector; task wording alone does not select a different model. When no provider, model, effort, or required restriction has been selected and no known tier override is exposed, omit the override and inherit the parent model. Once a target or restriction is selected, inability to honor it leaves the pass unavailable; it does not authorize inheritance or substitution.

If the user's or project's active instructions or the live prompt name a model for this subagent, use that model instead of the default tier above. They can name it by the subagent's tier, by its prompt-asset name, or for the subagents being dispatched. Without such an instruction, a model configured for this subagent's role takes precedence over the default tier.

A generic subagent is one whose whole brief is the prompt you send it. When the host's subagent tool makes you name an agent, use only a name you have seen the host list, and list its agents before the first dispatch if you have not. Pick the plain one that adds no role of its own, which still counts as a generic subagent. Never pick a specialist, such as a reviewer or worker agent, whose own role prompt, output format, or tool limits would replace or narrow your prompt.

**T3 Code.** When the model named for a reviewer needs a provider or reasoning setting the native subagent tool cannot set, and T3 Code's `orchestrator_capabilities` and `delegate_task` are callable, read `references/t3-dispatch.md` and dispatch that reviewer through `delegate_task` with `isolation: shared`. It gets the same prompt asset and returns the same output; a requested provider, model, or effort that T3 cannot serve leaves that pass unavailable, with the reason reported and no substitute dispatched. Reviewers on the session's own provider stay native.

**Bounded dispatch.** Each reviewer starts in a fresh subagent whose context holds only its own rubric and inputs. The one exception is the combined reviewer that `references/single-pass.md` chooses below a size cutoff, which is itself one reviewer. Otherwise do not combine reviewers in one prompt, and do not send a reviewer to an agent that already ran another. Queue the reviewers and launch only as many as the harness accepts at once. A concurrency or active-agent-limit error means the harness is full, not that the reviewer failed: leave the reviewer queued and retry after a slot frees. A full harness is not a reason to run a reviewer inline. When a dispatch cannot recover through active work, supported release, or a corrected invocation, report that pass unavailable. An inline pass may replace it only when no provider, model, effort, or required restriction was selected for that reviewer; disclose the change.

**Agent lifecycle.** Collect terminal outcomes, including failures, before cleanup. Close or release review-owned agents when the harness provides caller-owned cleanup, before refilling slots, advancing stages, or returning. Do not message completed agents with no remaining work. Do not infer released capacity from completion or interruption, or invent cleanup operations.

**Permission mode.** Omit the `mode` parameter on the dispatch call so the user's configured permission settings apply.
